## Goal
Family members sign in with a 6-digit code sent to their email and share one household (ADR-013). The instance owner is fixed by
`DEALSCOUR_OWNER_EMAIL`, so a stranger can't claim a fresh deployment. The owner invites others with a link code.
`current_household_id()` comes from the signed-in user instead of the constant 1. Every API except health and auth requires a session.

## Runtime boundary
Server-side. Times via `clock.now()`. Secrets via `config.py` only. **Never log or return** a code, token or hash, except `LogSender`,
which prints the code **only** when `DEALSCOUR_DEV_LOGIN=1` (and the app logs a loud warning at startup when that is on).
No new dependencies: use `secrets`, `hashlib`/`hmac`, `smtplib`, `email.message`.

## Settings (config.py)
`secret_key` (`DEALSCOUR_SECRET_KEY`, required unless dev login. Startup error if missing in non-dev), `owner_email`
(`DEALSCOUR_OWNER_EMAIL`, lowercased), `dev_login` (`DEALSCOUR_DEV_LOGIN == "1"`), `cookie_secure` (`DEALSCOUR_BASE_URL` starts with https),
`smtp_host/port/user/password/from` (`SMTP_*`).

## Schema
- `app_user`: `id`, `email` unique (lowercased, trimmed), `name` str|null, `created_at`.
- `household_member`: `household_id` FK, `user_id` FK, `role` `"owner"|"member"`, PK (household_id, user_id).
- `login_code`: `id`, `email`, `code_hash` (HMAC-SHA256(secret_key, email + ":" + code)), `expires_at` (+10 min), `attempts` int=0,
  `used_at` null, `created_at`.
- `auth_session`: `id`, `token_hash` unique (SHA-256 of the token), `user_id` FK, `created_at`, `expires_at` (+30 days), `last_seen_at`.
- `invite`: `id`, `code_hash` unique (SHA-256), `household_id` FK, `created_by` FK, `expires_at` (+7 days), `used_by` null, `used_at` null.

## Endpoints
- `POST /api/v1/auth/request-code` `{email, invite_code?}` → **always 202 `{"sent": true}`** (no account enumeration). A code is created and
  emailed only if: (a) the email is a known user, or (b) it equals `owner_email` and there is no owner yet, or (c) `invite_code` is valid
  and unused. Rate limit: at most 5 codes per email per hour (beyond that, silently don't send). Codes are 6 digits from `secrets`.
- `POST /api/v1/auth/verify` `{email, code, invite_code?, name?}` → on success: creates the user if needed (owner bootstrap: the user becomes
  `owner` of household 1. Invite: `member` of the invite's household, and the invite is marked used), marks the code used, creates a session,
  sets cookie `ds_session` (HttpOnly, SameSite=Lax, Secure per settings, Path=/, Max-Age 30 days) → 200 `{user, household_id, role}`.
  Failure → 400 `{"detail": "Invalid or expired code"}`. Each wrong attempt increments `attempts`, and after 5 the code is dead.
  Compare with `hmac.compare_digest`.
- `POST /api/v1/auth/logout` → deletes the session, clears the cookie. `GET /api/v1/auth/me` → `{user, household_id, role}` or 401.
- `POST /api/v1/households/invites` (owner only, else 403) → `{invite_code, expires_at}`. The code is 10+ chars from `secrets.token_urlsafe` and is shown once.
- `GET /api/v1/households/members` → members of the caller's household (email, name, role).
- `DELETE /api/v1/households/members/{user_id}` (owner only. The owner can't remove themselves) → removes membership and deletes that user's sessions.

## Session + CSRF dependencies
- `current_user` reads the cookie, looks up `token_hash`, checks expiry, and updates `last_seen_at` at most once per hour → else **401**.
- `current_household_id` = the user's household (one per user for now). A user with no membership → 403.
- **CSRF:** every POST/PATCH/DELETE under `/api/v1` except `auth/request-code` and `auth/verify` requires header `X-DealScour: 1` → else 403.
  (SameSite=Lax plus a custom header that cross-site forms can't send.)
- Apply `current_user` to all routers except health and auth. The deals and plans routers too (catalog prices now depend on the household's observations).

## Test cases (write first). Use a fake EmailSender that captures (email, code), and a frozen clock.
1. Owner bootstrap: owner_email requests a code → sender called once. Verify → 200, role owner, household 1, cookie set with HttpOnly and SameSite=Lax.
2. A stranger email (not owner, no invite) → 202 and **no email sent**. Verify with any code → 400.
3. Wrong code 5× → the 6th attempt with the **right** code fails (400). Expired code (clock +11 min) → 400. Used code reused → 400.
4. Rate limit: the 6th request-code within an hour sends nothing. After +61 min it sends again.
5. Invite: owner creates an invite → a new email requests with invite_code → verify with name → role member of the same household.
   Reusing the same invite for another email → no code sent (202) and verify 400. Expired invite (+8 days) → same.
6. Non-owner creating an invite → 403. Removing a member deletes their sessions (their next request → 401).
7. Protected routes: `GET /api/v1/lists` without a cookie → 401. With a cookie → 200. POST without `X-DealScour` → 403. With it → 201.
8. Isolation: two households (owner of hh1 invites A; a second owner set directly in the DB for hh2) → A can't see hh2's lists, offers, baskets or prices (404/empty).
9. Session expiry (+31 days) → 401. Logout → cookie cleared, session row gone, next request 401.
10. Nothing secret in responses or logs: assert the code/token never appears in any JSON response and in caplog (except with dev_login on).
11. Existing suites pass using the new authenticated client fixture.
12. Migration 0004 upgrades from 0003 with data intact. Existing household 1 data stays owned by household 1.
